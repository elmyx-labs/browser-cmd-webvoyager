# browser-cmd on WebVoyager: technical report

browser-cmd with a Codex gpt-6.1-sol agent completes 611 of 615 WebVoyager tasks (99.35%) under the leaderboard's GPT-5.5 judge, with no site-specific knowledge given to the agent and the browser-cmd build frozen for every counted attempt.

## Results

Every judge scores the same 615 trajectories, one counted attempt per task. Three of the four judges place the result above the current top entry, browser-control (Fable 5) at 610/615 (99.19%), and the fourth ties it.

| Judge | Role | Passed | Score | Not passed |
| --- | --- | --- | --- | --- |
| GPT-5.5, Alumnium vanilla prompt | leaderboard judge (same as the top entry) | 611/615 | 99.35% | Booking--9, GitHub--13, Google Search--14, Wolfram Alpha--33 |
| gpt-5.6-sol | cross-check, same prompt | 612/615 | 99.51% | GitHub--13, Google Search--14, Wolfram Alpha--33 |
| Claude Opus 5.5 | cross-check, other model family | 610/615 | 99.19% | BBC News--4, BBC News--17, GitHub--13, Google Map--5, Google Search--14 |
| Gemini 3.8 Flash | cross-check, run once on the final set only | 613/615 | 99.67% | GitHub--13, Google Search--15 |

- All four judges pass 607 tasks. Only GitHub--13 fails under all four. A majority of three or more judges passes 612 tasks.
- The GPT-5.5 and Gemini rows come from the pinned omxyz `auto_eval.py` (commit `df42681`): one screenshot per task, `max_completion_tokens` 2000. The gpt-5.6-sol and Opus rows use the same pinned prompts through `harness/validation/judge.py`, on subscription CLIs instead of the API.
- Gemini was reached through OpenRouter, with only the model name and the API base URL changed. Under the 2000-token cap, 3 of its answers (ArXiv--14, Booking--9, Wolfram Alpha--43) were cut off by hidden reasoning before any verdict and parsed as failures (610/615). Those 3 tasks were re-judged with an 8000-token cap and all passed; the row above uses those verdicts.
- Gemini's Google Search--15 verdict text ends in SUCCESS. The official parser marks it NOT SUCCESS because it finds the substring "NOT SUCCESS" in the agent's quoted phrase "login was not successful" (`evaluation/auto_eval.py`, line 183). We report the parser's result unchanged.
- No verdict was edited by hand under any judge.

`python3 scripts/verify.py` recounts every row from the judges' own outputs.

## System under test

The agent is a stock Codex CLI session that drives a real Chrome only through browser-cmd. The browser-cmd binary, its skill and its plugin are byte-identical in every counted attempt.

| Component | Setting |
| --- | --- |
| Actor | Codex CLI 0.163.0, model gpt-6.1-sol, reasoning effort high, one fresh session per task |
| Actor isolation | Own `CODEX_HOME` per task; personal and bundled skills disabled; no MCP servers; sub-agents off |
| Browser | browser-cmd daemon per task; fresh headless Chrome and profile per task; pace 0.3 |
| Skill | The harness's compact browser-cmd skill (`harness/runner/skills/lean/SKILL.md`, about 930 words: the command set, a plan-and-pace routine and general rules), installed for Codex as `.agents/skills/browser-cmd/SKILL.md`; names no benchmark site |
| Other tools | Shell, and Codex's built-in web search. The prompt forbids `site:` operators and reading the task's website through search; that website is read with browser-cmd. |
| Reviewer | gpt-6.1-terra, up to 2 rounds; sees the task, the answer, the last 8,000 characters of the agent's notes and the final screenshot; cannot browse; the actor checks each point in the browser |
| Time limit | 900 s per task; at 180 s before the end the actor is told to finish with what it has |
| Evidence | One final screenshot (`final.png`) and the answer file (`ANSWER.txt`) per task, as the judge requires |

**Frozen build.** Every run recorded `source.tar.gz`, the exact browser-cmd source, skill and plugin the run was built from. The snapshots of all counted runs, the main run and every rerun, are identical file for file; the snapshot is published in `snapshot/`. The skill the actor read is not in that snapshot but in the harness; its SHA-256 (`3cd714ca…`) is recorded in every run's manifest and is the same in all of them. Between the main run and the last attempt only the benchmark harness changed (the runner, its reviewer and the validation judge).

The agent's whole knowledge of the benchmark sites is what the model learned in training. The prompt, the skill and the reviewer contain no site names, URLs, selectors, page layouts or per-site tips.

## What we did not do

The score comes from the frozen system on the leaderboard's own task file and judge, with nothing removed or corrected by hand.

- **No code change to the system under test.** The browser-cmd binary, skill and plugin were frozen at the start of the main run and stayed byte-identical (source snapshots above).
- **No task removed by us.** All 615 tasks of the top entry's task layer are scored, byte-for-byte as published at omxyz/webvoyager `df42681`.
- **No task reworded by us.** The only text change is a mechanical year roll on 49 Booking and Google Flights tasks whose dates had passed (next section). No meaning, constraint or object of a task was edited.
- **No verdict corrected.** Every judge's verdict is reported as parsed, including the two parser artefacts noted under Results.
- **No site knowledge.** No per-site skill, prompt, selector, URL list or reconnaissance notes.
- **No human in the loop during a task.** For 2 tasks an operator signed in to a Chrome beforehand (next section); nobody acted during any task.
- **No best-of-N.** Where a task has several attempts, the latest one counts whatever its verdict, including attempts that turned a pass into a fail.
- **No attempt hidden.** Every attempt from the main run on, including the aborted round 3, is kept with its trajectory, screenshot, reviewer verdicts and token usage.

## Task set and environment

The tasks are the top entry's own 615-task file; the run happened outside the US, so part of the traffic went through a US residential proxy.

**Tasks.** `benchmark/data/current/WebVoyager_data.jsonl` is byte-for-byte `benchmark/data/current/WebVoyager_data.jsonl` of omxyz/webvoyager at `df42681` (SHA-256 `3be3e587…`). It covers 15 sites, 39 to 46 tasks each.

**Date roll.** Booking and Google Flights cannot search a date that has passed. On those two sites only, every explicit date in a task is moved forward by whole years until the earliest is not in the past, as of 2026-10-27. This changed 49 tasks (19 Booking, 30 Google Flights), each by one year; for example "October 1 to October 4, 2026" became "… 2027". The full list with before and after text is in `benchmark/data/browser-cmd/date_updates.json`. Dates on other sites are historical questions and were left as published. The judge is reference-free, so the roll changes what can be run, not how it is scored.

**Time zone.** The browser and the agent's shell run in America/New_York.

**Network.** Without a US residential address, several sites refuse or reroute the session before the agent acts (Allrecipes answers HTTP 402; others show bot walls or a regional site). The harness therefore routes traffic through a US residential proxy (IPRoyal, sticky 30-minute sessions):

- whole tasks on 4 sites: Allrecipes, Cambridge Dictionary, ESPN and GitHub;
- whole tasks for 2 tasks whose route leads to such a site: Google Search--14 and Google Map--11;
- for every other task, only requests to transfermarkt, target.com and walmart.com.

All other traffic, including all other sites, goes out directly. In the final set, 167 tasks carried proxy traffic.

**Prepared browser (2 tasks).** Cambridge Dictionary--39 (the Word Scramble game in the Plus section) and GitHub--40 (the sign-up form) stopped in the main run at a security-verification loop and a "temporarily restricted" page. Their counted attempts ran in a headful Chrome that the operator had opened and signed in to GitHub, Cambridge Dictionary and Amazon beforehand, attached through CDP (`--cdp`), on the operator's own network. The agent started each task from a clean tab set; the operator did nothing during the tasks. This mirrors a user running the agent in their own browser.

## Harness changes after the freeze

After the main run, only the harness changed: the actor's answer instructions, the reviewer's prompt, runner plumbing and the validation judge's parser. Each rule is general and names no site, but each was written after reading specific failed tasks, and its wording examples come from them.

| Before | Change | Prompted by |
| --- | --- | --- |
| Round 1 (R1) | The answer leads with the best item found and states its difference, instead of opening with a negative. A task that asks for an action shows the page confirming it. "Change account data" narrowed to data the task does not ask to change. Every reviewer verdict is saved with its cost. `--cdp` attaches an operator-prepared Chrome. | ArXiv--42, Coursera--8, Huggingface--19 (good item, answer devalued it); Amazon--15 (item added, screenshot showed the product page); Cambridge Dictionary--39, GitHub--40 |
| Round 2 (R2) | Only filters the task names narrow the result; a filter the site lacks is applied by checking candidates in the site's own order. | GitHub--13, Booking--9 |
| Round 3 (R3) | Two readings that give different results are answered for each, the likelier first. Facts come from the named website, figures from the page with arithmetic shown. The chosen item is the best by the task's measure. A time window the site offers is widened before another measure is substituted. A claim that something does not exist names the page that would hold it. | Booking--9 (per night or in total), Coursera--26 (one course or the program), ESPN--40, Wolfram Alpha--33, BBC News--4, Google Map--5, Google Search--37, GitHub--13, ArXiv--11 |
| Round 3 (runner) | A Codex session ending on HTTP 429 is marked rate-limited and left for `--resume`, not scored as a timeout. | The aborted round 3 |
| Round 4 (R4) | A count is one number, counted on the list or index the site keeps, not a lower bound; the reviewer asks for it. | BBC News--17 ("at least 7" in round 3) |
| Judging, before the composite was scored | Validation judge only: the verdict is the last one stated, so an Opus answer that says a point "doesn't change the verdict" is read right. The main run and the reruns therefore ran under different harness prompts: 594 counted attempts under the main-run prompt, 21 under later ones. Each task directory keeps the exact prompt it ran with (`prompt.txt`); `harness/` holds the final version of the runner.

## Why we consider this measurement fair

The score is one system, frozen, on the leaderboard's own tasks and judge, cross-checked by judges outside the
actor's model family, with every attempt and verdict published.

- **The system under test never changed.** The browser-cmd source, binary and skill are identical in every counted
  attempt (`snapshot/`, `browser-cmd.lock.json`). Only the harness around it changed between rounds.
- **The tasks were fixed before any run.** The only change to any task is a deterministic roll of 49 past dates,
  computed before execution and listed task by task in `TASK_UPDATES.md`. No task was removed, reworded or
  re-dated after a result was seen.
- **Reruns are disclosed task by task, and the latest attempt counts.** A rerun replaced the earlier attempt
  whatever its verdict: one rerun turned a pass into a failure (BBC News--17 in round 3) and was counted as such
  until the next round. The ledger below gives every rerun, why it was needed and what changed.
- **Harness changes are general rules.** Each rule is a sentence about answers and evidence that names no site,
  and applies to every task; none adds knowledge of a site.
- **The reruns moved the result on few tasks.** Of the main run's failures (under GPT-5.5, or under gpt-5.6-sol
  where GPT-5.5 did not score the main-run attempt) that now pass under GPT-5.5, 6 are tasks where the agent's answer or its evidence fell short (Amazon--15,
  ArXiv--42, Coursera--8, Coursera--26, Google Search--37, Huggingface--19), 2 tasks that needed a signed-in
  browser (Cambridge Dictionary--39, GitHub--40) and 2 tasks judged a day after they ran (ArXiv--1, ArXiv--9).
  Seven more were reruns for failures under Opus alone, which GPT-5.5 had already passed.
- **Four judges, three model families.** The actor is an OpenAI model and so is the leaderboard judge, so the
  same trajectories were also scored by Claude Opus 5.5 (Anthropic) and Gemini 3.8 Flash (Google), with the
  same pinned prompt. The lowest of the four, Opus, gives 610/615; the highest, Gemini, 613/615.
- **Every verdict is as the judge gave it.** No verdict was edited, overridden or re-asked; the two parser
  artefacts are reported as parsed.
- **Every claim can be checked offline.** `scripts/verify.py` recounts all four scores from the judges' raw
  outputs and checks every counted attempt's evidence, with no API key.

## Limitations

The result is one counted attempt per task on live websites, scored by LLM judges, so it shows what the system can do, not a success rate with error bars.

- **One attempt per task, no repeat statistics.** Repeating full runs on live sites costs about a day and a week's Codex allowance each. Without repeats we cannot separate the system's variance from the sites' and the judges'.
- **Reruns covered failed tasks only.** A rerun can also turn a pass into a failure: BBC News--17 did so in round 3, and GitHub--13 passed under Opus before round 3 and failed after. Passing tasks were not rerun, so such flips among them are not observed.
- **Harness rules were written on this benchmark's failures.** There is no held-out task set. The rules are general and name no site, but their examples come from the failed tasks listed above.
- **Two harness versions are mixed.** 594 counted attempts ran under the main-run prompt, 21 under later ones.
- **LLM judges drift.** Four judges spread over 3 tasks; one judge moves with the day it runs and with how its text is parsed. The judges are reference-free, so a fluent wrong answer with a matching screenshot can pass.
- **Live sites change.** Pages, stock and rankings differ from day to day; an exact rerun is not possible, and some tasks (GitHub--13, Google Search--14) can no longer be answered as written.
- **Environment matters.** The proxy and the prepared browser stand in for a US home connection and a user's own signed-in browser. Without them, part of the benchmark fails before the agent acts.
- **The agent may search the web.** Codex's built-in web search was on for sources the task does not name; the task's own website was read only through browser-cmd.
- **Entries are not like-for-like.** Leaderboard entries differ in task sets, judges, attempt counts and environments. Ours uses the top entry's task file and judge, which makes that one comparison the closest.

The actor's sandbox could read the host's temporary directory; in one transcript (Huggingface--9) the actor listed it, and that listing is replaced with a note. To reproduce, place the harness as `bench/` in a browser-cmd checkout (the runner builds browser-cmd and loads its plugin from there):

```sh
mkdir browser-cmd && tar xzf snapshot/browser-cmd-source.tar.gz -C browser-cmd && cp -R harness browser-cmd/bench
cd browser-cmd/bench/runner
BROWSER_CMD_PROXY=<US residential proxy URL> python3 run.py --out runs/codex-gpt-6.1-sol \
  --host codex --model gpt-6.1-sol --effort high --web-tools --review gpt-6.1-terra \
  --timeout 900 --timezone America/New_York --as-of 2026-10-27 --workers 3
python3 run.py --out runs/codex-gpt-6.1-sol --resume            # re-executes execution errors only
OPENAI_API_KEY=... python3 ../webvoyager/judge.py runs/codex-gpt-6.1-sol
```

`--as-of` fixes the date the roll is computed from, so every attempt saw the same task text.
